GhostAir Auth API

Hey — welcome. This is your integration reference for the GhostAir auth backend. By the time you're done reading, you'll be able to wire up registration, email verification, login, session refresh, and password recovery from any web or mobile client. Copy the snippets, match the shapes, ship the flow.

New here? Skim Overview, then jump to Quickstart — it's a full end-to-end flow you can paste into a browser and run in under a minute.

Overview #

GhostAir is a JSON HTTP API served under /api/v1. You authenticate with a bearer JWT, and if you're calling from a browser the same tokens are also set as HttpOnly cookies — so you don't have to touch them from JavaScript at all. Every response has a predictable shape, and every error you get back carries a user-ready message you can render straight into your UI.

Base URL

plaintext
https://ghostair.onrender.com/api/v1

Point your client at this URL. It's the hosted production instance — check with the backend team if you need a separate staging environment for your build.

Response format #

Response envelope

Every response you'll get back — success or failure — has the same shape. Type it once in your client and reuse it everywhere.

Success

200 OK
{
  "success": true,
  "message": "Logged in successfully",
  "data": { /* endpoint-specific payload, or null */ }
}

Failure

4xx / 5xx
{
  "success": false,
  "message": "Validation failed",
  "details": [
    { "field": "email", "message": "Please provide a valid email address" }
  ]
}

When details shows up, it's either an array of { field, message } objects (validation errors — highlight each field in your form) or an object with endpoint-specific hints (for example { verificationRequired: true, email } — route the user to the verify screen). Don't assume details is present; always check success first.

Sending requests

Four rules to follow every time you call the API:

  • Send every request body as JSON — set Content-Type: application/json.
  • On protected endpoints, attach Authorization: Bearer <accessToken>.
  • If you're in a browser, use credentials: "include" — the auth cookies will ride along automatically and you can skip the Authorization header entirely.
  • Keep your request body under 10 KB. Anything larger gets rejected — trim it first.

Quickstart #

Here's the shortest path from zero to a logged-in user. Paste this into your browser client and you're done — it registers, verifies, logs in, and fetches the current user in one flow. Cookie-based auth is assumed; if you're building for a native app, grab data.tokens.accessToken from the login response and send it as a bearer header on the calls that follow.

javascript — register → verify → login → me
const API = "https://ghostair.onrender.com/api/v1";

const api = (path, body) =>
  fetch(`${API}${path}`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    credentials: "include",
    body: JSON.stringify(body),
  }).then((r) => r.json());

// 1. Sign the user up. They will receive a 6-digit OTP by email.
await api("/auth/register", {
  firstName: "Ada",
  lastName:  "Lovelace",
  email:     "ada@example.com",
  password:        "Analytical!Engine1",
  confirmPassword: "Analytical!Engine1",
});

// 2. Confirm the OTP the user typed into your form.
await api("/auth/verify-email", {
  email: "ada@example.com",
  otp:   "482913",
});

// 3. Log in. Cookies are set automatically; tokens also come back in the body.
await api("/auth/login", {
  email:    "ada@example.com",
  password: "Analytical!Engine1",
});

// 4. Fetch the current user. With cookies you need no header at all.
const me = await fetch(`${API}/auth/me`, { credentials: "include" })
  .then((r) => r.json());

Auth model #

Every user you onboard walks through three states: registered → verified → authenticated. Only verified users can log in. You drive each transition with an explicit endpoint call — nothing happens implicitly, so what you see in your code is exactly what the backend does.

lifecycle
register  ─────────┐
                   ▼
               verify-email  ─────┐
                                  ▼
                                login ──► access + refresh
                                          │
                                          ├─► refresh (rotation)
                                          └─► logout / change-password
                                              (both revoke the refresh token)

Tokens & sessions

  • Access token — short-lived (15 minutes). Send it as Authorization: Bearer on protected endpoints.
  • Refresh token — longer-lived (7 days). Exchange it at /refresh for a new pair when the access token expires.
  • Both are also set as HttpOnly cookies, which means JavaScript cannot read them. In a browser, just send credentials: "include" and forget they exist.
  • The refresh cookie is scoped to /api/v1/auth, so it is only sent to auth endpoints.
Rotation. A successful /refresh issues a brand new access and refresh token and invalidates the previous refresh. If you're storing tokens yourself, overwrite the old refresh token as soon as the response comes back — using it twice will log the user out.
When to log the user out. If any request returns 401 and /refresh also returns 401, clear local session state and route to the login screen. Don't retry — the session is gone.

Password policy

Every password your user submits — on registration, reset, or change — has to clear these rules. They're strict on purpose, so mirror them in your form to give instant feedback:

  • 8–128 characters
  • At least one uppercase letter (A–Z)
  • At least one lowercase letter (a–z)
  • At least one digit (0–9)
  • At least one special character — !@#$%^&*(),.?":{}|<>_\-+=[]/\`~;'
  • No whitespace
  • Not present in the built-in weak-password list

When a password fails, you'll get back the exact rules that broke — render them inline instead of a generic "weak password" toast. Want to score a password without submitting the form? Hit the password strength endpoint and you'll get the same evaluation back, perfect for a live strength meter.

OTP handling

OTPs are 6-digit numeric codes we send to your user by email. Build your OTP input with these rules in mind:

  • Each code lives for 10 minutes. Show your user a countdown so they don't wonder if it's still valid.
  • You get 5 attempts per code. The error message tells you how many are left — surface it in the UI so your user knows the stakes.
  • After the 5th wrong attempt, the code is dead. Prompt your user to request a fresh one via /resend-verification.
  • Requesting a new code kills the old one and is throttled to once every 60 seconds. Disable your "Resend" button and count down — don't make your user guess.

Email previews

This is exactly what your user sees in their inbox. Each preview below is the real HTML the server sends, rendered inside an isolated frame — click a tab to swap templates. Use these as a visual reference when you design the matching in-app screens (OTP input, "code sent" toast, etc.) so the whole flow feels like one product.

Error codes

Every error you get back carries a human-readable message. Show it to your user verbatim — it's already written for end-user eyes, so you don't need to rewrite anything.

StatusWhat it means for your UI
400Validation error, wrong or expired OTP, wrong current password. Show message; if details[] is present, highlight each field.
401Missing/expired token or wrong login credentials. On protected routes, try /refresh once; if that also fails, sign the user out.
403Email not verified, or user lacks permission. If details.verificationRequired is true, route to the verification screen.
404Resource not found — usually a bad email on /verify-email.
409Duplicate resource. On registration this is a taken email.
423Account is temporarily locked after too many bad logins. Show the message (it includes wait time) and disable the login button briefly.
429Rate limit hit or too many wrong OTP attempts. Back off and disable the trigger until the user waits.
Don't leak account existence. /forgot-password always returns the same success response, whether or not the email is registered. Mirror that in your UI — show the same confirmation screen regardless.

Rate limits

These are the ceilings you'll want to design your client around. Every response you get back includes the standard RateLimit-Limit, RateLimit-Remaining, and RateLimit-Reset headers — read them from your fetch response and render a friendly countdown for your user instead of a hard error.

WhereWindowMax requests
Any auth endpoint15 min20
/login15 min10 per email
OTP resend1 hour6 per email
Password reset endpoints1 hour5 per email

Login has one extra safety net you should know about: if your user gets their password wrong five times in a row, we lock the account for 15 minutes — no matter which client or IP the requests came from. When that happens, you'll get a 423 back with the exact wait time in the message. Surface that to your user instead of a generic "try again".

Endpoints #

Every endpoint you'll need, grouped so you can scan the reference and copy the shape into your client. The colored pill on each card tells you what auth you need: Public means no token, Bearer means an access token, and Refresh token means the refresh cookie (or body field).

POST /api/v1/auth/register Public

Call this when your user hits "Sign up". You create the account, we send them a 6-digit OTP by email. Heads up — the account starts in an unverified state, so your user can't log in yet. You'll want to route them straight to your OTP-entry screen and finish the flow with /verify-email.

Request body

firstNamestring, 2–50 chars, letters + ' - space.
lastNamestring, 2–50 chars, same character set.
nameoptional display name (2–120 chars). Defaults to firstName lastName.
emailvalid email; case-insensitive; must be unique.
passwordmust satisfy the password policy.
confirmPasswordmust exactly match password.

Example

request
POST /api/v1/auth/register
Content-Type: application/json

{
  "firstName":       "Grace",
  "lastName":        "Hopper",
  "email":           "grace@example.com",
  "password":        "Nanoseconds!1906",
  "confirmPassword": "Nanoseconds!1906"
}
201 Created
{
  "success": true,
  "message": "Account created. We sent a verification code to your email.",
  "data": {
    "user": { "id": "...", "email": "grace@example.com", "isVerified": false },
    "verification": {
      "required":          true,
      "email":             "grace@example.com",
      "expiresInMinutes":  10
    }
  }
}

Errors

  • 400 — validation failure. details[] lists each offending field.
  • 409 — email already registered.
POST /api/v1/auth/verify-email Public

Take the OTP your user typed into your form and POST it here. On success we flip the account to verified — from that moment on, your user can log in. Send them straight to the login screen (or auto-log them in if you want a smoother onboarding).

Request body

emailthe address that received the code.
otp4–8 digit numeric string.
200 OK
{
  "success": true,
  "message": "Email verified successfully. You can now log in.",
  "data": { "user": { "..." } }
}

Errors

  • 400 — expired code, no active code, or a wrong code (message includes remaining attempts).
  • 404 — no account matches that email.
  • 429 — five wrong attempts on the same code; request a new one.
POST /api/v1/auth/resend-verification Public

Your user lost the code or it expired? Hit this endpoint to fire off a fresh OTP. Keep in mind: you get one resend per user every 60 seconds, so disable your "Resend" button and show a countdown until it's ready again.

Request body

emailthe account to notify.
200 OK
{
  "success": true,
  "message": "A new verification code has been sent to your email.",
  "data": { "expiresInMinutes": 10 }
}
POST /api/v1/auth/login Public

Hand off your user's email and password, get back a token pair (and the same tokens as cookies, if you're in a browser). A quick warning: five wrong passwords in a row and we lock the account for 15 minutes — so be gentle with the "Try again" copy in your UI and lean on the message the API returns.

Request body

emailaccount email.
passwordplaintext password.
200 OK
{
  "success": true,
  "message": "Logged in successfully",
  "data": {
    "user": { "..." },
    "tokens": {
      "accessToken":  "eyJhbGciOi...",
      "refreshToken": "eyJhbGciOi..."
    }
  }
}

Those same tokens are also written to accessToken and refreshToken cookies for you. If you're a browser client, just send credentials: "include" on every request and forget the body tokens exist — the cookies do all the work.

Errors

  • 401 — wrong credentials (message includes remaining attempts before lockout).
  • 403 — account is unverified. details.verificationRequired is true.
  • 423 — account is locked. Message states the wait in minutes.
POST /api/v1/auth/refresh Refresh token

Your access token expired? Call this to swap your refresh token for a fresh pair. In a browser we read the token from the refreshToken cookie automatically; on native, put it in the request body as a refreshToken field.

Successful refresh invalidates the presented refresh token. Store the new one immediately. If two clients try to refresh with the same token, only the first wins; the second is treated as a compromised replay and clears the session.
200 OK
{
  "success": true,
  "message": "Session refreshed",
  "data": {
    "tokens": { "accessToken": "...", "refreshToken": "..." }
  }
}

Errors

  • 401 — missing, expired, or revoked refresh token.
POST /api/v1/auth/logout Bearer

End your user's session — we revoke the refresh token and clear the auth cookies for you. One gotcha: the access token itself keeps working until it naturally expires (up to 15 minutes). So the moment you get a 200 back, drop any cached user state on your client. Don't wait for a 401 to figure it out.

200 OK
{ "success": true, "message": "Logged out successfully", "data": null }
POST /api/v1/auth/forgot-password Public

Kick off password recovery for your user. To keep attackers from probing your user list, we return the exact same 200 response whether or not the email is actually registered — so mirror that in your UI: always show a neutral "if it exists, we sent it" screen, never a "no such user" error.

Request body

emailthe account email.
200 OK
{
  "success": true,
  "message": "If an account exists with that email, a password reset code has been sent.",
  "data": { "expiresInMinutes": 10 }
}
POST /api/v1/auth/reset-password Public

Finish the recovery flow. Take the OTP your user got from /forgot-password and the new password they just typed, and POST them together here. On success, we kill every one of their active sessions and fire off a "password changed" alert email — so route them back to the login screen after you get the 200.

Request body

emailaccount email.
otpthe reset code.
passwordnew password (satisfies the policy, and must differ from the current one).
confirmPasswordmust match.
200 OK
{
  "success": true,
  "message": "Password reset successfully. You can now log in with your new password.",
  "data": null
}

Errors

  • 400 — expired, missing, or wrong OTP; new password equals current password; validation failure.
  • 429 — too many wrong OTP attempts.
POST /api/v1/auth/change-password Bearer

Let your user rotate their password from inside the app. You'll need the current password too — that's proof of possession, not busywork. When it succeeds, we revoke every session your user has open (including this one), so plan to route them back to the login screen right after.

Request body

currentPasswordthe existing password.
newPasswordsatisfies the policy; must differ from current.
confirmPasswordmust match newPassword.
200 OK
{
  "success": true,
  "message": "Password changed successfully. Please log in again.",
  "data": null
}
GET /api/v1/auth/me Bearer

Fetch your currently-signed-in user. This is your go-to for the "am I still logged in?" check when your app boots — hit it on mount, if you get a 200 you know your user's session is alive and you have their profile ready to hydrate the UI.

200 OK
{
  "success": true,
  "message": "Authenticated user profile",
  "data": {
    "user": {
      "id":          "66e0...",
      "firstName":   "Grace",
      "lastName":    "Hopper",
      "name":        "Grace Hopper",
      "email":       "grace@example.com",
      "role":        "user",
      "isVerified":  true,
      "lastLoginAt": "2026-09-06T10:14:22.031Z"
    }
  }
}
POST /api/v1/auth/password-strength Public

Score a password on the fly. Wire this behind your sign-up form (throttled — don't fire it on every keystroke) to power a live strength meter and inline hints. Nothing you send here gets stored, so it's safe to call while your user is still typing.

200 OK
{
  "success": true,
  "message": "Password evaluation",
  "data": {
    "valid":    false,
    "strength": "fair",
    "failed":   ["at least one special character (e.g. !@#$%)"],
    "checks": {
      "minLength":  true,
      "uppercase":  true,
      "lowercase":  true,
      "number":     true,
      "special":    false,
      "noSpaces":   true,
      "notCommon":  true
    },
    "suggestions": ["Add at least one special character (e.g. !@#$%)."]
  }
}

strength is one of weak, fair, medium, strong, very-strong. Treat anything below medium as submit-blocked in your UI.

Client-side security #

A few things you'll want to lock down on the frontend so this API stays secure end-to-end. Treat this list as a checklist before you ship:

  • Reach for cookies, not bearer tokens, in browsers. Send credentials: "include" and let the HttpOnly cookies do the work — your JavaScript can't read them, which means XSS can't steal them either.
  • Never park tokens in localStorage or sessionStorage. If you absolutely have to hold them yourself (mobile, non-browser client), put them in the platform's secure storage — Keychain, Keystore, or equivalent.
  • Always talk to this API over HTTPS in production. Cookies are marked Secure, so a plain-HTTP call will silently arrive with no session — and you'll spend the next hour wondering why nothing works.
  • Handle a 401 deliberately. Try /refresh exactly once; if it also fails, wipe your local user state and send your user to the login screen. Don't loop.
  • Respect the rate limits. Debounce your login and "Resend OTP" buttons, and honour RateLimit-Reset before you retry — otherwise you'll trip a 429 and frustrate your user.
  • Validate on the client, trust the server. Mirror the password policy in your sign-up form so your user gets instant feedback, but never assume your check is enough — we recheck everything on the backend.
